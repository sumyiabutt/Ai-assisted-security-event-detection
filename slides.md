# CyberFox — five-slide deck

Each slide has a title, three to four bullets, and a speaker note that can be read aloud.

---

## Slide 1 — The problem

**Detection is not the hard part; triage is.**

- A small team can collect far more log events than it can review by hand.
- Repeated failed logins, port sweeps, request floods and odd-hour access look different
  from each other but all hide inside the same flat CSV.
- Reviewers need one ranked queue with a reason, not four separate tools.
- Goal: a working prototype that validates logs, detects these four behaviours and explains
  every alert it raises.

> **Speaker note:** This project starts from a practical problem. We already have event data;
> what we lack is a fast, explainable way to decide what deserves attention. CyberFox takes a
> CSV of login, web and connection events and turns it into a ranked alert queue. It is a
> defensive prototype built to be demonstrated, not a production SIEM.

---

## Slide 2 — Architecture

**One pipeline from raw CSV to a security dashboard.**

- A validating parser accepts only well-formed rows and reports rejected rows with line
  numbers.
- Four rule detections and an Isolation Forest model run independently on the same events.
- The engine merges both alert sets, marks suspicious events and calculates severity counts.
- Results are stored in SQLite and rendered by Flask pages for dashboard, alerts and analysis.

> **Speaker note:** The parser is the only component that touches untrusted input. Valid rows
> go to two independent detectors: a deterministic rule engine and a behavioural ML model.
> The engine merges their alerts and writes runs, events, alerts and rejected rows to SQLite.
> The Flask app has three views on top of that store: an overview dashboard, a filterable
> alert queue, and an upload/preview/result flow. The bundled sample is analysed
> automatically on first start so the dashboard is never empty.

---

## Slide 3 — Detection methods

**Four explainable rules, one behavioural model, one MITRE mapping.**

- Brute force: 5+ failed logins in 10 minutes, Critical if a success follows — T1110.
- Port scan: 15+ distinct ports per IP — T1046. Request flood: 60+ events per minute — T1498.
- Off-hours successful login between 23:00 and 05:00 — T1078.
- Isolation Forest scores each IP on five features: total events, failed logins, distinct
  ports, peak requests/minute and off-hours logins; severity follows a 0–100 relative score.

> **Speaker note:** Every threshold is visible in the code and in the README, and every rule
> alert carries a MITRE technique. The ML side analyses source IPs, not individual rows. It
> uses 200 trees, a contamination setting of 0.2 and a fixed random seed so reruns are
> reproducible. Each ML reason names the most unusual feature, for example "25 distinct ports
> versus a median of 4". That explanation is what makes the model useful to an analyst rather
> than a black box.

## Slide 4 — Results on the bundled dataset

**Strong recall; precision is the honest trade-off.**

- 2,000 events: 1,883 benign, 117 malicious, 29 source IPs, 19 users.
- 12 alerts: 4 Critical, 4 High, 3 Medium, 1 Low; 173 events flagged as suspicious.
- Rules: precision 1.000, recall 1.000, F1 1.000.
- ML: precision 0.676, recall 1.000, F1 0.807; combined matches ML.

| Approach | TP | FP | FN | Precision | Recall | F1 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Rules | 117 | 0 | 0 | 1.000 | 1.000 | 1.000 |
| ML | 117 | 56 | 0 | 0.676 | 1.000 | 0.807 |
| Combined | 117 | 56 | 0 | 0.676 | 1.000 | 0.807 |

> **Speaker note:** The rules detect every malicious row because the synthetic attacks were
> generated to match the documented thresholds — perfect scores here are a sanity check, not
> a claim about real traffic. The ML model catches every attack but raises 56 false-positive
> events from one benign internal host whose behaviour looks unusual next to its peers. That
> is exactly the trade-off a real tuning exercise would address. Combined equals ML because
> any event covered by either detector counts, and ML already covers every attack IP. All 46
> automated tests pass.

## Slide 5 — Conclusion and next steps

**A complete, working prototype with room to grow.**

- End-to-end flow is delivered: validation, detection, storage, dashboard, alerts and upload
  analysis.
- Every alert is generated by real detection logic and every metric comes from the project's
  own evaluation script.
- Next: connect a real log source, tune thresholds with analyst feedback, add alert
  acknowledgement.
- Then: authentication, CSRF protection and a production deployment.

> **Speaker note:** The deliverable is not a mock-up. It runs, it stores results, it shows the
> alert queue and it explains each alert. The limitations are equally clear: synthetic data,
> one contamination setting, no authentication and no live ingestion. The next milestone is
> to replay real, authorised logs and tune the thresholds against analyst judgement. CyberFox
> is designed for defensive research with synthetic or authorised data only.
